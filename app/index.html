Research interpretation

+1 is the 320×256 foreground/occlusion mask. The drawing routines extract its bits at the car position, combine them with the car/sprite mask and use the result in the BOB/blitter path so the car can pass behind scenery.

+2 is code-proven as a packed 2-bit map at 160×112 logical cells, covering 320×224 gameplay pixels at 2×2 pixels per cell. This is why a 1-bit rendering produces artificial vertical stripes. Values 0–3 select normal, collision-correction and two slowdown responses.

+3 is code-proven as a 40×28 byte lookup indexed by x>>3, y>>3. Out-of-bounds returns use cardinal heading values, strongly identifying it as a direction/heading recovery grid rather than a bitmap mask.

The first three descriptors in each race record feed the AI/path code and reference six-byte records. The coordinate setup has now been traced: car X is optionally negated according to race word +$6A, then the 16.16 X origin at +$62 is added; Y receives the 16.16 origin at +$66. The resulting high words are what the nearest-waypoint routine compares with waypoint +0.w and signed +3.b. The viewer therefore follows +$6A automatically for its provisional left/right display mirror. X/Y scale and display origin are still research controls rather than proven screen-projection semantics. Byte +2 & $7F behaves as route/progress metadata, not heading. Word +4 is used as a relative link after setup; its static pre-runtime encoding remains under investigation. All earlier waypoint contact sheets should be treated as superseded.

The boot code copies the decrunched main image to runtime $1000, so path pointers map back to this file image by subtracting $1000. The stored descriptor span is count×6; the nearest-point routine uses DBF and appears to inspect one extra boundary record, which remains under investigation.
